# Профиль BreakProject

`punishments.yml` подготовлен по пользовательскому конфигу для нашей сборки
Grim `simfix11`. Он содержит 124 отдельные включённые проверки. Их нарушения
больше не суммируются между разными проверками. `Phase`, отсутствовавший в
исходном профиле, оставлен выключенным. Незарегистрированные Baritone и
Autoclicker не добавлены.

## База и history

Следующие восемь проверок продолжают работать, но не сохраняют новые нарушения
в базу и `/grim history`:

- Simulation;
- GroundSpoof;
- NoFall;
- Timer, TimerLimit, NegativeTimer, TickTimer, VehicleTimer.

Для 24 проверок BadPackets стоят `5:5 [log]` и `5:5 [alert]`: запись в БД/history
и алёрт при достижении 5, 10, 15 и следующих порогов активных нарушений.
Остальные 92 включённые проверки используют `1:1 [log]`. Их запись не зависит
от того, достигнут ли порог алёрта или вебхука. NoSlow, AntiKB, AntiExplosion,
PacketOrder, Reach и Hitboxes также сохраняются. Само наличие флага в истории
не означает, что его причина уже подтверждена.

База и `/grim history` используют одни и те же сохранённые нарушения. Отдельной
«полной history без записи в базу» здесь нет. Этот профиль не удаляет старую
историю, сессии игроков или данные имён.

В существующем `database.yml` должны быть включены `database.enabled` и
маршруты `database.routing.violation` / `database.routing.session` на рабочие
бекенды. Сохрани свои текущие маршруты и реквизиты подключения. Если раньше
настраивалось дополнительное прореживание записей, выставь внутри существующих
секций следующие значения:

```yaml
database:
  enabled: true
  write-path:
    violation-store-min-interval-ms: 0
    violation-store-min-interval-per-check: {}
  history:
    group-interval-ms: 30000
```

Это фрагмент для объединения с текущим файлом, а не замена всего `database.yml`.
`group-interval-ms` группирует вывод истории и не удаляет отдельные записи.
Сохранение также зависит от доступности хранилища и очереди записи.

В simfix11 исправлена обработка `1:1`: каждое подходящее срабатывание выполняет
команду и после затишья, когда старые нарушения вышли из пятиминутного окна.
В более ранней сборке команда могла перестать выполняться после уменьшения
активного счётчика. Для полной записи истории нужен этот фикс вместе с профилем.

## Уведомления

Во всех секциях окно активных нарушений — 300 секунд. Интервалы ниже считаются
отдельно для каждого игрока и каждой проверки:

| Проверки | Алёрт: первый / шаг | Discord и proxy: первый / шаг | База |
|---|---:|---:|---|
| Восемь шумных проверок выше | 300 / 300 | 1000 / 1000 | нет |
| Reach, Hitboxes | 1 / 1 (каждый флаг) | 5 / 50 | каждый флаг |
| AntiKB, AntiExplosion | 10 / 50 | 50 / 100 | каждый флаг |
| NoSlow | 20 / 50 | 50 / 100 | каждый флаг |
| Post, PacketOrderA–O | 50 / 100 | 100 / 200 | каждый флаг |
| BadPackets | 5 / 5 | 40 / 100 | 5 / 5 |
| Crash | 10 / 50 | 40 / 100 | каждый флаг |
| Остальные включённые | 20 / 50 | 50 / 100 | каждый флаг |

Например, `20:50 [alert]` уведомляет при достижении 20, 70, 120 активных
нарушений. Это не интервал в секундах и не жёсткий глобальный лимит сообщений.
В существующей логике следующий порог не уменьшается при частичном истечении
нарушений; повторное взведение интервальной команды происходит после падения
активного счётчика ниже её первого порога. Для `1:1` в simfix11 действует
правило «каждое срабатывание».

В `discord.yml` оставь текущий URL вебхука и проверь `enabled: true`. Сам URL
не включён в этот профиль. `[proxy]` работает при уже настроенной передаче
оповещений через прокси. Его пороги совпадают с вебхуком.

`/grim verbose` показывает каждый флаг даже при высоком пороге `[alert]`.
Для обычного наблюдения выключи verbose и используй `/grim alerts`.
Чтобы также не дублировать уведомления в консоль, можно изменить существующие
поля `config.yml`:

```yaml
alerts:
  print-to-console: false
verbose:
  print-to-console: false
```

Сохрани остальные поля этих секций, включая настройки proxy.

## Наказания и установка

Бан-команды Reach и Hitboxes сохранены буквально из исходного конфига:
`10:5 bban-ip %player% 14d -p --sender-name=&fꐞ&f Использование &7стороннего&f ПО.`
Их пороги не зависят от более редкой отправки уведомлений.

1. Установи JAR simfix11 вместо текущего JAR Grim и перезапусти сервер.
2. Сохрани резервную копию серверного `plugins/GrimAC/punishments.yml`.
3. Замени его этим `punishments.yml` целиком. При объединении со старыми
   группами одна проверка может попасть сразу в две секции и дублировать запись.
4. Проверь настройки базы и Discord, описанные выше. При изменении backend
   или маршрутов базы используй перезапуск сервера.
5. Для изменения только `punishments.yml` достаточно `/grim reload`.
6. Открой `/grim history <ник>` после нового сохранённого нарушения.

Если твой каталог данных Grim называется иначе, используй файл в нём.
Профиль создан локально; серверные файлы, база и Discord не изменялись.

## Проверка профиля и исправления

Файл разобран SnakeYAML с запретом повторяющихся ключей. Сопоставление с
зарегистрированными проверками проверено по правилам текущего PunishmentManager:
124 отдельные активные секции, ноль пересечений, восемь без `[log]`, 24 BadPackets
с `5:5 [log]` и `5:5 [alert]`, 92 с `1:1 [log]`, две исходные бан-команды.
Общий прогон `:common:test` для исправления simfix11 прошёл:
173 теста, ноль ошибок и пропусков. В том числе шесть тестов исполнения команд;
три из них воспроизводили пропуски `1:1` до исправления.
